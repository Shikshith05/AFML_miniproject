# AFML SLM: grouped-query attention and DPO in a 28M-parameter model

A small decoder-only language model (Llama-style: RMSNorm, RoPE, SwiGLU, tied
embeddings; 8 layers, d_model 512, vocab 4096) trained from scratch on
TinyStories, used to study two things:

1. **Grouped-query attention (GQA) vs multi-head attention (MHA).** Two
   pretraining runs that differ only in how attention is built: MHA with 8 K/V
   heads, GQA with 2. Both have exactly 27,795,968 parameters (GQA spends the
   K/V parameters it saves on a wider FFN, decision S7). Same seed, data order
   and token budget. Compared on quality (validation loss) and on cost (KV-cache
   size, decode speed, memory).
2. **Alignment of the GQA model:** supervised fine-tuning (SFT) on instruction
   data, then Direct Preference Optimization (DPO) on in-domain story pairs,
   evaluated side by side against the base model.

Every design decision and its reasoning is in [docs/decisions.md](docs/decisions.md).

*The 1 Nov benchmark measures the default `repeat_interleave` path: GQA

## Setup

Python 3.11, PyTorch >= 2.5 recommended. GQA expands K/V with
`repeat_interleave` by default on any torch; `SLM_SDPA_ENABLE_GQA=1` opts in
to SDPA's `enable_gqa` (torch >= 2.5), which was slower on a T4 (decision S14).

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1            # Linux/macOS: source .venv/bin/activate
pip install torch                     # pick the CUDA/CPU build from pytorch.org
pip install -r requirements.txt
pip install -e .                      # makes `slm` importable for the tests
```

All commands below run from the repo root. Every script also runs on CPU
(with a warning), but training is only practical on a GPU. The project was
run on a Kaggle **T4** (16 GB, fp16 — Turing has no bf16) with the notebooks in
[notebooks/](notebooks/): `afml_kaggle_training.ipynb` for data, pretraining
and the benchmark, and `track_d_kaggle.ipynb` for SFT, pairs, DPO and
evaluation. Both are meant for *Save Version → Save & Run All*.

### 1. Data pipeline

Byte-level BPE tokenizer (vocab 4096) + TinyStories token files. Details and
measurements: [docs/track_a_notes.md](docs/track_a_notes.md).

```powershell
# Full pipeline (~13 min): 1% val holdout (seed 1337) -> ftfy text cleaning ->
# tokenizer trained on the train side only -> data/train.bin, data/val.bin, data/meta.json
python scripts/prepare_data.py --train-tokenizer

# Sanity check: decode random val windows, fertility, <unk> rate
python scripts/inspect_data.py

# Tests (no dataset needed)
python -m pytest tests/test_tokenizer.py -q
```

The tokenizer is committed at `artifacts/tokenizer/tokenizer.json`, so
teammates can skip retraining it and just run
`python scripts/prepare_data.py` (it checks the tokenizer was trained on the
same split before using it). The tokenizer can also be trained on its own with
`python scripts/train_tokenizer.py [--max-stories N]`.

Smoke run on 20k stories, kept away from the real outputs:

```powershell
python scripts/prepare_data.py --limit 20000 --train-tokenizer --out-dir data/smoke --tokenizer data/smoke/tokenizer.json
python scripts/inspect_data.py --data-dir data/smoke --tokenizer data/smoke/tokenizer.json
```

Using the data from training code:

```python
from slm.data.tinystories import make_get_batch

get_batch = make_get_batch("data", batch_size=16, seq_len=512, device="cuda")
x, y = get_batch("train")   # int64 [16, 512] on cuda; y is x shifted left by one
```

`make_batch_provider(cfg)` does the same from track C's `Config`.

### 2. Pretraining (MHA and GQA)

Same settings for both runs (decisions S5, S11, S12): micro-batch 85, no
accumulation, 12,000 steps (522M tokens, about 1.1 epochs), fp16, seed 1337.

```powershell
python scripts/pretrain.py --preset mha --run-name mha_base --micro-batch-size 85 --grad-accum-steps 1 --max-steps 12000 --precision fp16
python scripts/pretrain.py --preset gqa --run-name gqa_base --micro-batch-size 85 --grad-accum-steps 1 --max-steps 12000 --precision fp16
```

Checkpoints every 1,000 steps (`checkpoints/<run>/step_*.pt`, plus
`final.pt`); a killed run resumes from the newest one on restart. Add
`--dry-run` to print the resolved config only. `scripts/probe_batch_size.py`
finds the largest batch that fits a new GPU. On Kaggle use
`afml_kaggle_training.ipynb` (sections 3–5).

### 3. Attention benchmark

MHA vs GQA back to back on one GPU, random weights (no checkpoints needed):
training throughput, then KV-cache size, decode tokens/s and peak memory for
contexts 128–2048 and batches 1–64.

```powershell
python scripts/benchmark_attention.py           # default repeat_interleave path
$env:SLM_SDPA_ENABLE_GQA = "1"                  # opt-in enable_gqa path (bash: SLM_SDPA_ENABLE_GQA=1 python ...)
python scripts/benchmark_attention.py
```

The default `--out` follows the K/V path: `results/benchmark_repeat_interleave`
or `results/benchmark_enable_gqa`. It refuses to overwrite an existing
`benchmark.json`; `results/benchmark/` is the 1 Nov run on the
`repeat_interleave` path. The JSON records torch version, the K/V path used
(`kv_path`, `sdpa_enable_gqa`), whether torch supports `enable_gqa`, the
environment variable, git commit and date. On Kaggle: section 7 of
`afml_kaggle_training.ipynb`.

Finding (Kaggle T4, sm_75, torch 2.11): the `enable_gqa` path runs SDPA on
the math backend. Against MHA, GQA training was −39.1% (spread 3.5%,
`--train-batch 48`), training peak memory +58%, decode slower at all 20
configs (−17% to −71.3%, worst at context 1024, batch 64), and context 2048,
batch 64 ran out of memory where the `repeat_interleave` run completed. The
KV cache is exactly 4x smaller on both paths. Hence `repeat_interleave` is
the default; Ampere or newer (FlashAttention) is untested.

### 4. Supervised fine-tuning

```powershell
python scripts/sft.py --preset gqa --checkpoint checkpoints/gqa_base/final.pt                                         # Alpaca -> gqa_sft
python scripts/sft.py --preset gqa --checkpoint checkpoints/gqa_base/final.pt --dataset oasst1 --run-name gqa_sft_oasst1  # human-written
```

`--dataset alpaca | dolly | oasst1`. `--run-name` names the output folders
(`checkpoints/<run-name>/`, `results/<run-name>/`), so runs on different data
never overwrite each other. Prompt tokens are masked out of the loss; the run
prints a masking check before training. `--dry-run` builds and checks the data
only; `--limit N` uses N rows.

### 5. Preference pairs

```powershell
python scripts/build_preference_data.py --weak-checkpoint checkpoints/gqa_base/step_002000.pt
```

3,000 pairs from held-out TinyStories stories: chosen = the real ending,
rejected = the step-2000 checkpoint's ending from the same 48-token opening,
both in the SFT template (decisions S3, S8). The committed
`data/preference/pairs.jsonl` is the set used for all results.

### 6. DPO

```powershell
python scripts/dpo.py --sft-checkpoint checkpoints/gqa_sft/final.pt                                       # -> gqa_dpo
python scripts/dpo.py --sft-checkpoint checkpoints/gqa_sft_oasst1/final.pt --run-name gqa_dpo_oasst1      # oasst1 chain
```

The SFT model is both the starting policy and the frozen reference. Reference
log-probs are computed once and cached in `data/ref_logprobs_*.npz` (a separate
file per run name), fingerprinted with the pairs and the reference model's
weights, so a stale cache is recomputed and never reused (S9). Before training
the test loss must be 0.693 (= log 2).

### 7. Evaluation

```powershell
python scripts/evaluate.py --base checkpoints/gqa_base/final.pt --sft checkpoints/gqa_sft/final.pt --dpo checkpoints/gqa_dpo/final.pt
python scripts/evaluate.py --base checkpoints/gqa_base/final.pt --sft checkpoints/gqa_sft_oasst1/final.pt --dpo checkpoints/gqa_dpo_oasst1/final.pt --out results/eval_oasst1
```

For each model: perplexity on 500 held-out stories, samples on 12 fixed
prompts (same seed per prompt), and preference accuracy on the 200 held-out
pairs; plus DPO's implicit-reward accuracy against SFT (S10). Writes
`metrics.json`, `samples.json`, `samples.md` to `--out` (default `results/eval`).

### 8. Generate

```powershell
python scripts/generate.py --ckpt checkpoints/gqa_base/final.pt --ckpt checkpoints/gqa_sft/final.pt --ckpt checkpoints/gqa_dpo/final.pt --prompts-file data/demo_prompts.txt --out results/generations.md
python scripts/generate.py --ckpt checkpoints/gqa_sft/final.pt --prompt "Write a story about a red ball."
```

Each model is built from the config stored in its checkpoint (CPU or GPU,
`--device`). SFT/DPO checkpoints get the SFT prompt template and base
checkpoints the raw text (`--template auto|always|never`). Prompt *k* uses
seed + *k* for every model, so the comparison is fair. Sampling:
`--temperature` (0 = greedy), `--top-k`, `--max-new-tokens`.

### 9. Figures and tables

```powershell
python scripts/make_results.py
```

Reads only `results/` and rebuilds every figure (`.png`, `.pdf`) and table
(`.md`, `.tex`). New folders (`results/eval_oasst1`,
`results/benchmark_enable_gqa`, `results/gqa_sft_oasst1`, …) are picked up
automatically. Each benchmark is captioned with the K/V path it measured:
`results/benchmark` (1 Nov) as the repeat_interleave (default) path, and
`results/benchmark_enable_gqa`, once committed, as "enable_gqa (opt-in) path,
T4", with a side-by-side table of the two (`tables/benchmark_side_by_side_enable_gqa`).

## Tests

```powershell
python -m pytest -q
```

About 30 s on a CPU, no datasets, checkpoints or GPU needed (one test is
CUDA-only and is skipped without a GPU). They cover the tokenizer and data
pipeline, attention (MHA/GQA/MQA against a reference, `repeat_interleave` vs the
`enable_gqa` opt-in, the default path and the opt-in switch), the model (causality, KV cache, parameter counts, an overfit check),
generation, SFT data parsing and masking, the DPO loss and reference cache,
the benchmark's provenance fields, the generation CLI and `make_results.py`.

## Datasets

| Dataset | Link | Used in |
|---|---|---|
