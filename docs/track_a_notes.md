# Track A notes: tokenizer + data pipeline

Running log of decisions and measurements for track A. To be folded into
`docs/decisions.md` once that branch is merged.

---

## 2026-10-24: Tokenizer: byte-level BPE, vocab 4096

**Chosen:** byte-level BPE trained with HF `tokenizers` (`ByteLevel`
pre-tokenizer + decoder, GPT-2 regex, no normalizer), vocab 4096 including
4 special tokens with fixed ids:

| token   | id |
|---------|----|
| `<pad>` | 0  |
| `<bos>` | 1  |
| `<eos>` | 2  |
| `<unk>` | 3  |

Byte-level means every string is encodable, so `<unk>` is never emitted
(measured: 0.0% of val tokens). It keeps id 3 only so the layout is fixed.
Every token id fits in uint16.

**Rejected: GPT-2's 50,257-token vocab.** At d_model=512 its embedding
matrix alone is 50,257 × 512 ≈ 25.7M parameters, which is the whole ~25M
budget, leaving almost nothing for the transformer blocks. Our 4096 vocab
costs 4096 × 512 ≈ 2.1M (tied with the LM head), about 8% of the model.
TinyStories has a very small working vocabulary, so the extra compression
from 50k tokens is tiny (see fertility below): GPT-2 needs about 2.5% fewer
tokens for the same text, which doesn't come close to paying for 12× the
embedding parameters.

**Also decided:** text that contains a literal `<eos>` (or another special
token string) is encoded as ordinary bytes. Special ids only come from
`add_bos` / `add_eos`. HF `tokenizers` otherwise matches special-token
strings inside raw text, even with `add_special_tokens=False`. This matters
for SFT/DPO data, where a response containing `"<eos>"` would otherwise
inject a real EOS.

## 2026-10-24: Train/val split

- Source: `roneneldan/TinyStories`, HF `train` split, 2,119,719 stories.
- Val = 1% of stories: `np.random.default_rng(1337).permutation(n_total)[:round(0.01 * n_total)]`,
  sorted. That gives 21,197 stories. Split fingerprint (sha256 of the int64
  indices, first 16 hex chars): **`37c59ce9ec55a6fd`**. It is recorded in
  `data/meta.json`, `data/split.json` and `artifacts/tokenizer/train_info.json`.
  The indices themselves are in `data/val_indices.npy` (gitignored, and
  regenerated by the same function).
- The split is made **before** tokenizer training, and the tokenizer is trained
  on the train side only. `prepare_data.py` refuses to use an existing
  tokenizer whose `split_hash` doesn't match.
- The split is always computed over the full dataset, even with `--limit`. A
  smoke run's val set is therefore a subset of the real val set, and no
  tokenizer ever sees val text.
- Empty or whitespace-only stories are skipped: 230 in total (227 train, 3 val).
- The HF dataset also has an official `validation` split (21,990 stories),
  which we do **not** use. It's available as an untouched test set if the
  paper needs one.

## 2026-10-24: Measurements (first full run, before text cleaning)

*Superseded by the cleaned run below. Kept for comparison.*

| | value |
|---|---|
| vocab size | 4096 |
| train stories / tokens | 2,098,295 / **483,082,605** |
| val stories / tokens | 21,194 / **4,866,321** |
| fertility (val, content tokens ÷ whitespace words) | **1.301** (1.313 counting `<bos>`/`<eos>`) |
| GPT-2 fertility on the same val text | 1.269 |
| avg tokens per story (incl. `<bos>`/`<eos>`) | 229.6 |
| `<unk>` rate | 0.0% |
| max token id | 4095 |

A 20k-story smoke run gave essentially the same fertility (1.301 vs GPT-2
1.264), so the tokenizer is not sensitive to training-set size here.

Timings (8-core CPU, Windows): tokenizer training on all 2.1M train stories
272 s; encoding 264 s; total 9.0 min after the dataset is cached (the first
download added about 4 min). `get_batch` takes about 1 ms per 16×512 batch on CPU.

**Implication for track C:** 483M train tokens. The draft `max_steps=20000`
× 128 × 512 ≈ 1.31B tokens is about **2.7 epochs**, not the single epoch the
`dropout=0.0` comment assumes. `get_batch` samples windows uniformly with
replacement, so there is no hard epoch boundary, but the repetition is real.

**Corpus quirk:** TinyStories v1 contains mojibake, e.g. `â€™` instead of
`’` (UTF-8 punctuation decoded as cp1252). With no normalizer, about 19 of
the 3,836 merges went to those fragments, and a correct curly quote costs
3 tokens. Normalizing it (fixing the mojibake and mapping curly quotes to
ASCII) would need a re-tokenize. **Fixed in the next entry.**

## 2026-10-24: Text cleaning with ftfy (tokenizer retrained, data re-encoded)

**What:** every story now goes through `slm.data.tinystories.clean_text`
before anything sees it. That happens in `iter_chunks`, the single
text-loading path used by both tokenizer training and `prepare_data.py`.
`clean_text` is `ftfy.fix_text()` with default settings, plus a one-line
pre-pass:

- **Why the pre-pass:** `”` is UTF-8 `E2 80 9D`, and `0x9D` has no cp1252
  character, so in TinyStories that byte was lost, leaving a bare `â€`.
  ftfy cannot restore a missing byte. Before a space it guesses `E2 80 A0`
  and outputs `†`. A `â€` that is not followed by a valid cp1252
  continuation character can only be a broken `”`, so the pre-pass restores
  it, and ftfy then handles it like any other quote. Without the pre-pass,
  about half of the affected stories (1,364 of the first 50k checked) still
  had mojibake or a spurious `†` after ftfy.
- ftfy's defaults also straighten curly quotes to ASCII (`’` → `'`, `“”` →
  `"`), NFC-normalize and fix line breaks. Dashes and ellipses (`–`, `—`, `…`)
  are kept as they are.
- Cleaning version `ftfy-6.3.1+rdquo-v1` is recorded in `data/meta.json` and
  `artifacts/tokenizer/train_info.json`. `prepare_data.py` refuses a tokenizer
  whose cleaning version or split hash doesn't match. `ftfy>=6.1` was added to
  `requirements.txt`.
- Cleaning runs in a process pool (8 workers, bounded batches, under
  `__main__`). It runs once per pass, adding about 1.5 min to tokenizer
  training and 2.7 min to encoding compared with the uncleaned run. Tested
  against the serial path.

**Split unchanged:** the split is over story indices, so the fingerprint is
still **`37c59ce9ec55a6fd`**. The story counts are identical too
(2,098,295 train / 21,194 val / 230 empty skipped).

**How many stories changed:** **130,107 of 2,119,719 (6.1%)**. Of those,
130,085 had mojibake (`â€…`, `Ã…`, `Â`) in the raw text. Almost all of the
other 22 had genuine curly punctuation.

**Residue:** the decoded val set has no `â€`/`Ã` sequences. One stray `Â`
byte is left at a story boundary out of 4.85M tokens, and it isn't worth a
special case. The 19 mojibake merges are gone. The only merges that decode
to non-ASCII are the shared byte prefix `E2 80` of `–` / `—` / `…`, which is
normal for byte-level BPE.

| | before cleaning | **after cleaning** |
|---|---|---|
| train tokens | 483,082,605 | **481,574,529** (−0.31%) |
| val tokens | 4,866,321 | **4,850,760** |
| fertility (val, content tokens ÷ words) | 1.301 | **1.297** (1.308 counting `<bos>`/`<eos>`) |
| GPT-2 fertility, same val text | 1.269 | 1.263 |
| avg tokens per story | 229.6 | 228.9 |
| `<unk>` rate | 0.0% | 0.0% |

Run time: tokenizer training 365 s, clean + encode 424 s, **13.2 min**
total. The epoch estimate for track C is unchanged: 1.31B / 481.6M ≈ 2.7
epochs.

**For other tracks:** `Tokenizer.encode` does **not** clean text, because
that keeps encode/decode exactly lossless. Any text fed to the model (SFT
data, eval prompts, DPO pairs) should go through `clean_text` first so it
matches the pretraining distribution. In particular, the model has almost
never seen a curly quote.

## Format contract (what other tracks rely on)

- `artifacts/tokenizer/tokenizer.json` (committed) plus `train_info.json`
- `data/train.bin`, `data/val.bin`: flat `np.uint16`; each story is
  `<bos> tokens <eos>`, concatenated. Windows span story boundaries;
  there is no cross-document attention mask.
- `data/meta.json`: `vocab_size`, `n_train_tokens`, `n_val_tokens`,
  `n_train_stories`, `n_val_stories`, `seed`, `tokenizer`, plus the split
  hash, special ids and timings
- `slm.data.tinystories.make_get_batch(data_dir, batch_size, seq_len, device)`
  → `get_batch(split)` → `(x, y)`, int64 `[B, S]` on `device`, `y = x`
  shifted left by one. Uses torch's global RNG (so saving and restoring the
  RNG state resumes the same batch stream), pinned memory plus
  `non_blocking` on CUDA. `make_batch_provider(cfg)` is the same thing driven
  by track C's `Config` (`cfg.data.train_bin/val_bin/max_train_tokens`,
  `cfg.train.micro_batch_size/device`, `cfg.model.max_seq_len`).
- `slm.tokenizer.tokenizer.Tokenizer.load(path_or_dir)` with `encode`,
  `encode_batch`, `decode`, `vocab_size`, `pad_id`/`bos_id`/`eos_id`/`unk_id`.

## How to reproduce

```powershell
python scripts/prepare_data.py --train-tokenizer   # ~13 min + first download
python scripts/inspect_data.py                     # windows, fertility, <unk> %
python -m pytest tests/test_tokenizer.py -q
```

To reuse the committed tokenizer and only regenerate the `.bin` files, run
`python scripts/prepare_data.py` without the flag. Check that `split_hash`
in `data/meta.json` is `37c59ce9ec55a6fd`. Retraining the tokenizer is
expected to reproduce it for the same input order and `tokenizers` version
(0.23.3 here), but that has not been checked bit-for-bit. Use the committed file.
