## 1. Generation — `src/slm/generation/generate.py`

**What the model outputs.** Token ids in, logits out, shape
`[batch, positions, 4096]`: one score per vocabulary token at every position.
For generating we only need the **last** position: 4096 scores for "what comes
next". Softmax turns scores into probabilities that sum to 1.

**`sample_next_token`: choosing one token.**
1. `temperature == 0` → **greedy**: take the argmax. Deterministic, but loops
   ("the dog was happy. the dog was happy.").
2. divide logits by **temperature**: T < 1 sharpens (safer), T > 1 flattens
   (more random).
3. **top-k**: everything below the k-th best score → −∞ → probability 0.
   Junk tokens can never be drawn.
4. softmax → `torch.multinomial` (a weighted dice roll).

Toy check we ran (logits 3, 2, 1, 0.5, −1): P(top word) was 0.86 at T=0.5,
0.62 at T=1, 0.42 at T=2; with top_k=2 only the two best words ever appeared.

**`generate`: the loop, and the KV cache.**
- **Prefill**: run the whole prompt once. Every layer writes its keys and
  values into the cache.
- **Decode**: feed only the newest token; attention reads earlier K/V from
  the cache. Without the cache, step n recomputes all n tokens (O(n²) work
  overall); with it each step is constant work.
- The cache stores K/V at `n_kv_heads`. GQA has 2 instead of 8 → **4× smaller
  cache**. That is GQA's whole practical benefit, and generation is where it
  shows up.
- Stops at `<eos>` (rows that finish early keep emitting eos so the batch
  stays rectangular) or at `max_seq_len` (512 — RoPE has no positions beyond
  what it was trained on).

**Test that proves it works** (`tests/test_generate.py`): greedy output with
the cache is **identical** to recomputing from scratch, for MHA, GQA and MQA.
If the cache, RoPE offsets or causal mask were wrong, this would fail.

Viva questions to expect:
- *Why not always greedy?* Repetition loops; sampling gives variety.
- *Why top-k as well as temperature?* Temperature alone still leaves tiny
  probability on 4000 junk tokens; summed over a long story one gets picked.
- *Why is the prompt the same length across a batch?* The model has no
  padding mask, so rows are kept unpadded (DPO pairs use a fixed 48-token
  opening).

## 2. SFT — `src/slm/data/alpaca.py`, `src/slm/training/sft.py` (written by C)

**Goal.** The base model only continues stories. SFT teaches it to answer
an instruction, using the same next-token loss on
`### Instruction: … ### Response: …` text.

**Loss masking.** Prompt tokens get label −100, so `cross_entropy` ignores
them: the model learns to *produce responses*, not instructions.
`assert_masking_sane` checks this loudly because a masking bug trains with a
normal-looking loss curve.

**Learning rate 2e-5** (vs 3e-4 pretraining): small, so the model learns the
format without forgetting how to write (catastrophic forgetting).

**Dataset.** Alpaca is generated by text-davinci-003 (synthetic). The TA
advised against synthetic data, so `--dataset dolly` (Dolly-15k, written by
Databricks employees) or `--dataset oasst1` (OpenAssistant, human
conversations; we take only first-turn, top-ranked English replies).
`iter_instruction_rows` is the only place that knows each dataset's column
names.

**Honest limitation.** Our model has only read children's stories. Dolly
questions about history or programming are far outside what it knows; the
length filters (instruction ≤ 64 tokens, response ≤ 192) keep the simplest
examples. Expect SFT to teach the *format* far better than the *content*.

## 3. Preference pairs — `src/slm/data/preference.py`

**Decision S3.** Standard preference sets (HH-RLHF) are adult assistant
dialogue — meaningless to a TinyStories model. So we build in-domain pairs:

- take a **held-out** story (HF *validation* split: pretraining used only the
  HF *train* split, so the model has never seen these)
- **opening** = first 48 tokens
- **chosen** = the real rest of the story
- **rejected** = what an **early checkpoint** (step 2000 of 12k, much worse)
  writes from the same opening

Both go into the SFT template with instruction "Continue the story.", so DPO
sees the same format as SFT (resolves the SFT/DPO mismatch).

Only stories that finish within 192 tokens are used, and the weak model gets
the same 192-token budget, so both sides have a chance to end naturally.

**Confound to report:** if rejected responses are systematically longer or
shorter than chosen, DPO can partly learn "prefer this length". `stats.json`
records the mean lengths of both.

## 4. DPO — `src/slm/training/dpo.py`

**The idea.** We want the model to prefer chosen over rejected, but without
drifting far from the SFT model (otherwise it could "win" by producing
garbage that happens to score well). So every probability is measured
**relative to a frozen reference** (the SFT model):

```
chosen_logratio   = log π(chosen)   − log ref(chosen)
rejected_logratio = log π(rejected) − log ref(rejected)
margin = β · (chosen_logratio − rejected_logratio)
loss   = −log σ(margin)
```

- `log π(y)` = **sum** of log-probabilities of the response tokens (prompt
  masked with −100, same as SFT) — `sequence_logprobs`.
- **β = 0.1** controls the pull back to the reference. Small β → the policy
  may move further.
- **Implicit reward** of a response = β · (log π − log ref). **Reward
  accuracy** = how often chosen's reward beats rejected's. This is the number
  to watch.

**Sanity values.** At step 0 the policy *is* the reference, so every log-ratio
is 0, margin 0, loss = −log σ(0) = **log 2 = 0.693**, reward accuracy 0 (ties).
The training log prints this; if it isn't 0.693, something is wrong.

**Why DPO instead of RLHF/PPO?** PPO needs a separate reward model plus RL
sampling in the loop. DPO shows the same objective can be optimised directly
on pairs with a classification-style loss — one model, ordinary backprop.

**Reference log-probs are cached** (`data/ref_logprobs_*.npz`). The reference
never changes, so computing it once means only one model is in GPU memory.
The cache stores a fingerprint of the pairs and recomputes if the pairs
change.

**Other choices:** lr 5e-6 (lower than SFT: small nudges), no weight decay
(decay would pull weights toward zero, not toward the reference), 1 epoch,
200 pairs held out as a test set.

**Tests** (`tests/test_dpo_loss.py`): loss = log 2 when policy = reference;
a hand-computed value; loss falls as chosen gains; the gradient raises
chosen and lowers rejected; a few optimizer steps on a tiny model make the
margin positive.

## 5. Evaluation — `src/slm/evaluation/`, `scripts/evaluate.py`

For each of base, SFT and DPO:

1. **Perplexity on held-out stories** (`perplexity.py`) — a forgetting
   check. Did fine-tuning damage story fluency? Uses the tail of the shuffled
   validation split; DPO pairs use the head, so no overlap.
2. **Samples on 12 fixed prompts** (`instruction_eval.py`) — same template,
   same seed per prompt, so the three models are directly comparable
   (`results/eval/samples.md`). Plus simple form metrics: length, how often
   the model ends by itself (eos rate), distinct-2 (repetition).
3. **Preference accuracy** on the 200 held-out pairs (`dpo_eval.py`): does
   the model give the real ending higher probability than the weak one?
   Reported two ways — summed log-prob (biased toward shorter responses) and
   per-token (length-neutral). If they disagree, length is driving it.
4. For DPO vs SFT: **implicit-reward accuracy**, DPO's own objective.

**Honest framing for the paper:** these metrics measure *form* and
*preference for real text*, not helpfulness. Read the samples.
